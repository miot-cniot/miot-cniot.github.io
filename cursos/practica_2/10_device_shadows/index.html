    10. As compoñentes das sombras de dispositivo

    O que sabemos até agora das sombras de dispositivo

    Na sección anterior, descubrimos o concepto de sombra do dispositivo: unha representación virtual dun dispositivo IoT que contén os últimos valores coñecidos dos atributos do dispositivo. Unha sombra de dispositivo é unha representación e rexistro do estado dun dispositivo nun momento específico no tempo. Unha sombra é un documento JSON que se usa para almacenar e recuperar información do estado actual dun dispositivo. O seu propósito principal é facer que o estado dun dispositivo estea dispoñíbel para aplicacións e outros servizos, tanto se o dispositivo está conectado a AWS IoT como se non. No caso de perda de conexión, os subscritores poden acceder aos últimos valores dos atributos e, cando se recupera a conexión, poden actualizarse no dispositivo os cambios de atributos realizados por un cliente.

    O servizo de sombra do dispositivo actúa como intermediario (como o avatar na sección anterior), permitindo que os dispositivos e as aplicacións recuperen e actualicen o estado dun dispositivo. As sombras viven na nube de AWS onde IoT Core accede a elas, lendo e escribindo nelas. Isto ilústrase usando o noso camión de xeados e IoT Core no seguinte diagrama.

    Nesta sección, analizamos máis de perto o funcionamento interno das sombras de dispositivos e como proporcionan os servizos que esperamos delas. Pero antes de explorar como podes crear sombras de dispositivos, imos mergullarnos no ciclo de vida dunha sombra fixándonos nas mensaxes comunicadas entre os dispositivos e AWS IoT Core.

    Ciclo de vida dunha sombra de dispositivo

    Ilustremos como os dispositivos e os clientes aproveitan a funcionalidade de sombra usando o noso escenario do camión de xeados. A continuación, móstrase un exemplo simplificado de intercambios de mensaxes entre dous dispositivos no camión (un sensor de porta e un actuador) e unha aplicación (a aplicación móbil do usuario).

    Esta é unha situación clásica. O dispositivo IoT envía unha mensaxe. Un cliente subscríbese a ela. Entón pérdese a conectividade. Mentres tanto, o cliente emite unha solicitude. Debido á infraestrutura de sombra existente, a solicitude lévase a cabo unha vez que se restablece a conexión co dispositivo.

    A secuencia de pasos é a seguinte:

    Paso 1: O sensor do camión actualiza o documento de sombra

    O sensor envía os seus datos ao tópico da sombra do dispositivo. Eses datos persistirán, aínda que o dispositivo estea sen conexión.

    Mensaxe: "estado, informado, estado da porta, aberto".

    Paso 2: A aplicación de usuario está subscrita ao tema

    A aplicación de usuario recibe a información de que a porta está aberta.

    Mensaxe: "estado, informado, estado da porta, aberto".

    Paso 3: A aplicación de usuario envía o estado desexado actualizado

    O camión está nunha zona con pouca cobertura de rede. Cando a aplicación de usuario publica unha mensaxe para "pechar a porta", o dispositivo non recibe a mensaxe. A solicitude para cambiar o estado é recibida polo documento de sombra.

    Mensaxe: "estado, desexado, estado da porta, pechar".

    Paso 4: O camión recupera a conexión a Internet

    Cando o camión recupera a conexión a Internet, o dispositivo le a sombra do dispositivo e actualiza o seu estado pechando a porta.

    Mensaxe: "estado, desexado, estado da porta, pechar".

    Paso 5: O dispositivo actualiza a sombra co seu novo estado

    O dispositivo envía o seu estado actual informado (porta pechada) á sombra do dispositivo. A aplicación de usuario recibe esta actualización.

    Mensaxe: "estado, informado, estado da porta, pechar".

    Unha vez que coñecemos o ciclo de vida dunha sombra de dispositivo, estamos xa prontos para explorar como crear unha sombra de dispositivo.

    Cando se crea unha sombra de dispositivo, debe seleccionarse o tipo de sombra que se quere. Pode seleccionarse entre unha sombra con ou sen nome. Cal é a diferenza? Cales son os casos de uso para cada tipo? Na seguinte sección dase resposta a esas preguntas.

    Sombras de dispositivo con e sen nome

    Hai dous tipos de sombras de dispositivos: Sen nome (clásica) e con none (nomeada). Cada cousa de AWS IoT só pode ter unha sombra sen nome.

    Os dispositivos IoT adoitan ter datos con varios estados, como a configuración do usuario, a configuración do fabricante ou o estado operativo. Cada un destes datos de estado precisa de ser accedido por diferentes usuarios ou con diferentes frecuencias. Con sombras nomeadas, poden crearse diferentes coleccións de estados dos atributos dos dispositivos.

    Pode dividirse unha cousa con moitos atributos en diferentes sombras con atributos agrupados loxicamente, cada un identificado polo seu nome de sombra. Como resultado, pode definirse o acceso só aos datos de estado necesarios cunha sombra específica cando sexa necesario e reducir o tamaño da sombra individual. As sombras de dispositivos máis pequenas significan menos tráfico e menos custo de mensaxería.

    Por exemplo, no noso escenario do camión de xeados, o sensor de temperatura podería ter as seguintes sombras de dispositivos:

    Nome da sombra Atributos incluídos (exemplos)
    truckSensorTemperatureHrdwr * Versión do firmware
    * Intensidade do sinal
    truckSensorTemperatureReadings * Temperatura actual
    * Lectura anterior
    * Marca temporal

    As sombras de dispositivos nomeadas son máis versáteis e ofrecen unha funcionalidade máis rica. Por exemplo, tamén se pode limitar o acceso aos atributos agrupándoos en diferentes sombras e usando políticas de control de acceso.

    Despois de ter feito unha definición básica dos tipos de sombra, imos analizar máis polo miúdo os elementos que forman o documento da sombra dun dispositivo.

    O documento da sombra de dispositivo

    A sombra dun dispositivo é un documento JSON que se usa para almacenar e recuperar información de estado para un dispositivo.

    Un documento de sombra de dispositivo contén os seguintes cinco elementos:

    • Estado do dispositivo [variábeis (atributos) e valores]: Hai dous estados posíbeis: desexado e informado.
    • Metadatos: Unha marca temporal para cada atributo incluído no nodo de estado.
    • Marca temporal: A data e hora en formato época na que AWS IoT xerou a mensaxe.
    • ClientToken: Un valor que permite emparellar unha mensaxe de solicitude cunha resposta dun cliente ou dispositivo.
    • Versión: A versión actual do documento da sombra do dispositivo compartida en AWS IoT. Increméntase en un ao respecto da versión anterior do documento.

    Na seguinte figura podes ver máis información sobre as compoñentes principais dunha mensaxe de sombra de dispositivo.

    Os elementos que se mostran na figura son:

    1. state

      Hai dous estados posíbeis que unha mensaxe pode conter, só un ou ambos ao mesmo tempo:

      • desired
      • reported

      Un nodo de estado contén unha serie de atributos para o dispositivo. Non hai que incluír todos os atributos en cada mensaxe, só os que sexan relevantes nun determinado momento.

    1. desired

      É o estado desexado do valor da variable de estado. Por exemplo, fixar a temperatura da carga do camión en 32. As aplicacións poden escribir nesta parte do documento para actualizar o estado dunha cousa sen ter que conectarse directamente á cousa.

    1. reported

      O estado informado representa os valores máis recentes dos atributos que o dispositivo comunicou ao IoT Core. As aplicacións len esta parte do documento para coñecer o estado dunha cousa.

    1. metadata

      Información sobre os datos almacenados na sección de estado do documento. Isto inclúe marcas temporais, en formato época, para cada atributo na sección de estado, o que permite saber cando se actualizaron por última vez.

    1. timestamp

      Indica cando AWS IoT enviou a mensaxe. Coa marca temporal da mensaxe e as marcas temporais dos atributos individuais nas seccións desexada ou informada, un dispositivo pode calcular a antigüidade dunha propiedade, aínda que non teña un reloxo interno.

    1. clientToken

      Pode usarse un token de cliente coa mensaxería baseada en MQTT para verificar que o mesmo token apareza nunha solicitude e na súa resposta. Isto garante que a resposta e a solicitude estean asociadas. Se se usa, poden emparellarse a solicitude e a resposta correspondente por medio do token de cliente.

    1. version

      O servizo de sombra de dispositivo admite o control de versións en cada mensaxe de actualización, tanto de solicitude como de resposta. Isto significa que con cada actualización dunha sombra, a versión do documento JSON increméntase.

    O uso do control de versións garante que:

    • Un cliente pode recibir un erro se intenta sobrescribir unha sombra usando un número de versión máis antigo. Infórmase ao cliente de que debe resincronizar antes de poder actualizar a sombra dun dispositivo.
    • Un cliente pode decidir non actuar sobre unha mensaxe recibida se a mensaxe ten unha versión inferior á versión almacenada polo cliente.

    Tópicos da sombra de dispositivo

    AWS IoT usa tópicos MQTT reservados para rastrexar e informar do estado dun dispositivo. Como recordatorio, un tópico reservado é un tópico usado por AWS IoT para operacións especiais. Os tópicos reservados para as sombras de dispositivos teñen o prefixo $aws/things.

    As sombras poden ser nomeadas ou sen nome (clásicas). Os tópicos utilizados por cada unha difiren só no prefixo do tópico. Esta táboa mostra o prefixo de tópico usado por cada tipo de sombra.

    Valor do prefixo Tipo de sombra
    $aws/things/thingName/shadow Sombra sen nome (clásica)
    $aws/things/thingName/shadow/name/shadowName Sombra con nome

    Os seguintes son os tópicos MQTT utilizados para interactuar coas sombras:

    • /get
    • /get/accepted
    • /get/rejected
    • /update
    • /update/delta
    • /update/accepted
    • /update/documents
    • /update/rejected
    • /delete
    • /delete/accepted
    • /delete/rejected

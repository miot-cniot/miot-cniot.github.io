    8. Gestión de las conexiones de dispositivos

    ¿Qué ocurre cuando se interrumpen las conexiones?

    ¿Alguna vez has utilizado la artimaña de "Estoy a punto de entrar en un túnel" para terminar una conversación desagradable en tu móvil? ¿O te has encontrado en una zona donde no hay cobertura móvil? La cuestión es que los dispositivos conectados como tu móvil se desconectan de la red de vez en cuando. Simplemente pasa.

    Hay formas de mitigar este tipo de interrupciones, p.ej. cuando tus amigos intentan contactar contigo u obtener una actualización de tu red social. Por ejemplo, puedes configurar un mensaje para tu buzón de correo. Si no estás disponible, tus amigos escuchan este mensaje hasta que puedan contactar contigo nuevamente. O tus amigos pueden consultar tu última actualización en las redes sociales hasta que puedas publicar una nueva actualización.

    En el mundo real de la IoT, los dispositivos se usan a menudo en entornos con conectividad de red poco fiable. Los dispositivos pueden desconectarse debido a la falta de suministro de energía, batería baja, pérdida de conexión u otros motivos. Esto provocará desconexiones abruptas del Message Broker sin saber si la interrupción fue forzada por el cliente o es realmente problemática. Es posible que no tengas forma de saber cuánto tiempo ha estado inactivo un dispositivo. En los casos de sensores de temperatura o presión, esto podría ser caro y peligroso.

    Afortunadamente, el protocolo MQTT tiene dos mecanismos que pueden mitigar algunos de estos problemas.

    El mecanismo Keep alive: "¿Aún me escuchas?"

    MQTT usa una conexión TCP/IP que normalmente el cliente deja abierta para que pueda enviar y recibir datos en cualquier momento.

    Si no hay mensajes ni datos que vayan y vengan durante un cierto período de tiempo, el cliente intentará confirmar su conexión con el broker generando un PINGREQ. El cliente esperará recibir un PINGRESP del broker, como se muestra en la siguiente imagen.

    Este período de tiempo entre intercambios se conoce como el período Keep Alive y es configurable.

    El mecanismo Keep Alive garantiza que la conexión entre el cliente y el broker esté abierta y que ambos sean conscientes de estar conectados.

    Por ejemplo, el cliente podría establecer su tiempo de Keep Alive en 60 segundos. Esto significa que cada 60 segundos, el cliente enviará un PINGREQ y esperará un PINGRESP del broker.

    Ahora, supongamos que hubo una interrupción en la conexión TCP entre el cliente y el broker.

    Si el broker no recibe una solicitud de ping del cliente dentro de ese período de Keep Alive especificado, el broker asumirá que la conexión TCP no funciona y desconectará el cliente, como se muestra en la imagen anterior.

    El mecanismo Last Will and Testament (LWT): "Fue un placer trabajar contigo"

    El Message Broker desconectará a los clientes que no respondan. De este modo, no hay misterio sobre si un cliente está funcionando o no.

    Idealmente, cuando un cliente se desconecta inesperadamente, debería enviarse una notificación a todas las entidades interesadas.

    Esta es la función del Last Will and Testament (LWT). El mensaje LWT se usa para notificar a los suscriptores un apagado inesperado del publicador.

    Cuando un cliente se conecta por primera vez al broker, el cliente configura un mensaje LWT que le indica al broker que publique un mensaje en un tópico. Después, una regla puede enviar un mensaje (a través de un servicio como Amazon SQS) a todos los suscriptores en el caso de una desconexión anormal o abrupta del cliente.

    Ejemplo de secuencia de acciones: Keep alive y LWT

    Para poner todos estos conceptos en perspectiva, vamos a revisar la secuencia de pasos en la conexión entre un dispositivo IoT (digamos nuestro sensor de temperatura del camión de helados) y el IoT Core.

    Paso 1: Conexión y tiempo de Keep alive

    El dispositivo se conecta al AWS IoT Core indicando el tiempo del período Keep alive.

    Paso 2: Parámetros del último deseo (LWT)

    El dispositivo, al conectarse al AWS IoT Core, proporciona lo siguiente:

    1. Tema para LWT (p.ej. /last/will/topic)
    2. Mensaje LWT
    3. Tipo de calidad de servicio (QoS): 0, mensaje enviado cero o más veces, o 1, mensaje enviado repetidamente hasta que se reciba una confirmación de entrega.

    Paso 3: Desconexión de la red

    El dispositivo se desconecta abruptamente del AWS IoT Core.

    Paso 4: IoT Core publica el mensaje LWT

    AWS IoT Core detecta esta situación y publica el mensaje LWT a todos los suscriptores del tema (p.ej. /last/will/topic).

    Paso 5: Se filtra el mensaje usando reglas

    Usando reglas IoT se procesa el mensaje recibido en el tema y se encamina a Amazon SNS.

    Paso 6: SNS envía correos electrónicos

    Amazon SNS envía correos electrónicos de notificación a los destinatarios configurados.

    ¿Qué has estado haciendo desde la última vez que hablamos?

    Los mecanismos Keep Alive y LWT ayudan a mitigar los problemas de conexión. Sin embargo, no almacenan ninguna información sobre el estado del dispositivo. ¿Qué ocurre con los otros atributos específicos del dispositivo? Tomemos, por ejemplo, nuestro camión de helados. El último estado recibido para la puerta del congelador es "abierta". ¿Está la puerta del congelador actualmente abierta o cerrada? ¿Cuál es la temperatura en el compartimento principal? Si enviaste una solicitud para cerrar la puerta del congelador, ¿se recibió antes o después de la interrupción de la conexión? ¿Necesitas enviar el comando una y otra vez hasta que la conexión vuelva?

    Puede ser muy útil conocer el último estado informado por un dispositivo, aunque el dispositivo esté sin conexión. Veremos en las siguientes secciones cómo AWS IoT da una solución a este problema.

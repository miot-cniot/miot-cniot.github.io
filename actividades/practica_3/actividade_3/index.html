    Actividade 3

    ACCESO REMOTO A UN DISPOSITIVO IoT USANDO UN TÚNEL SEGURO

    Obxectivo

    O obxectivo desta actividade é comprobar o funcionamento da funcionalidade de tunelamento seguro do AWS IoT Device Management, que permite conectarse remotamente e con seguranza aos dispositivos IoT para solucionar problemas, facer trocos na configuración, etc, aínda estando protexidos por un firewall.

    Nota

    Podes ver aquí a documentación da funcionalidade Tunelamento seguro.

    Introdución

    Antes de facer a parte práctica desta actividade, le o contido introdutorio do titorial:

    • 7. Acceso sincronizado a su dispositivo IoT con AWS IoT Device Management – Túnel seguro
    • 7.1 Lectura previa: Conceptos de tunelización segura en AWS IoT.

    Que se vai configurar nesta actividade?

    Unha vez que se crea un túnel seguro no AWS IoT, hai dúas maneiras de probar a conexión co túnel:

    • Usando a conexión SSH dispoñíbel na consola do AWS IoT.
    • Configurando nunha segunda instancia o proxy local para acceder ao túnel seguro.

    O seguinte diagrama mostra como sería a configuración do túnel seguro na segunda opción, que é a que se vai probar nesta actividade.

    Configuración do túnel seguro entre dúas instancias.

    Este escenario mostra os seguintes elementos:

    • A instancia 1, que é a que fai as veces de dispositivo IoT ao que queremos conectarnos (é dicir, o dispositivo destino). Esta é a instancia VSCode na que xa instalamos e configuramos o Device Client. Como o Device Client xa inclúe un proxy local, non precisaremos facer ningunha configuración adicional nesta instancia.
    • O túnel seguro co dispositivo IoT destino (instancia 1) xestionado polo AWS IoT. Cando se crea o túnel, o Device Client instalado no dispositivo subscríbese automáticamente a un tópico MQTT no que recibe unha notificación co token de acceso do cliente (CAT) ao túnel seguro. Este token é utilizado polo Device Client para establecer a conexión co túnel sen que sexa necesario usar un proxy local independente.
    • A instancia 2, que é a que fai as veces de dispositivo orixe desde o que un operador se conectaría ao dispositivo IoT a través do túnel seguro. Nesta instancia si que teremos que configurar o proxy local que nos permita conectarnos ao túnel e iniciar unha sesión SSH remota no dispositivo IoT.

    Os pasos que vamos seguir para configurar este escenario son:

    1. Configurar un túnel seguro no AWS IoT.
    2. Configurar un proxy local no dispositivo orixe (instancia 2).
    3. Abrir unha sesión SSH no dispositivo IoT destino (instancia 1) desde o dispositivo orixe (instancia 2).

    Configuración do túnel seguro no AWS IoT Core

    Para configurar o túnel seguro no AWS IoT Core fai o seguinte:

    1. Na consola AWS IoT escolle a opción Túneis seguros dentro do menú Accións Remotas no panel da esquerda.

    2. Crea un novo túnel seguro premendo en Crear túnel e indicando as opcións seguintes:

      • Método de configuración: escolle Configuración manual.
      • Informacións básicas: insire unha descrición para o túnel.
      • Configuración de destino
        • Adiciona o servizo SSH.
        • No Nome da cousa escolle deviceClientThing. Lembra usar o teu prefixo diante.
      • Duración do túnel: deixa o valor padrón (12:00). Ten en conta que cada vez que este tempo expire haberá que xerar novos tokens de acceso para o túnel.

      Propiedades do túnel.

    3. Descarga o token de acceso do cliente (CAT) do dispositivo orixe. O token do dispositivo IoT destino non é preciso descargalo xa que o Device Client do dispositivo xa o obtén do AWS IoT usando unha subscrición automática a un tópico MQTT, como se explicou anteriormente.

      Descarga do token de acceso ao túnel.

    4. Comproba que unha vez que se crea o túnel, o dispositivo IoT destino xa aparece conectado.

      Estado do túnel unha vez creado.

    Importante

    Antes de continuar toma a captura 1 que se pide para xustificar a actividade.

    Configuración do dispositivo de orixe

    Neste apartado vamos crear e configurar a instancia 2, unha instancia VSCode que faga as veces de dispositivo de orixe, é dicir, o dispositivo desde o que un operador se conectaría remotamente ao dispositivo IoT destino usando o túnel seguro.

    Creación dunha instancia VSCode

    Para crear a instancia fai o seguinte:

    1. Desde a consola de CloudFormation no AWS Academy Learner Lab, lanza unha instancia VSCode seguindo as instrucións do documento que se che proporcionou. Usa o nome secureTunnelingClient co teu prefixo diante para a pila de CloudFormation.

    Importante

    Antes de continuar toma a captura 2 que se pide para xustificar a actividade.

    Instalación do token de acceso na instancia

    Para instalar o token de acceso na instancia creada no apartado anterior fai o seguinte:

    1. Accede á consola da instancia e crea un directorio secure_tunnel en /home/ubuntu.

    2. Sube o token que descargaches cando creaches o túnel seguro ao directorio secure_tunnel creado no paso anterior.

      Nota

      Para subir o ficheiro do token escolle no Explorador de Ficheiros a opción Upload no menú de contexto do cartafol secure_tunnel.

    Conexión ao túnel seguro

    Para conectarnos ao túnel seguro desde o dispositivo orixe temos que instalar, configurar e executar o proxy local. Hai diferentes maneiras de facelo. Nesta actividade vamos usar unha imaxe Docker predefinida que xa ten o proxy local instalado.

    Fai o seguinte:

    1. Abre un terminal e instala Docker na instancia e engade o teu usuario ao grupo docker. 

      $ sudo apt install docker.io
$ sudo usermod -aG docker $USER

      Nota

      Se che aparece un diálogo preguntando “Which services should be restarted?”, usa a tecla do tabulador para escoller OK e acepta. Reiniciarase a sesión no navegador

    2. Reinicia a instancia.

      Nota

      Podes facelo desde a consola de EC2 ou desde o menú de EC2 no AWS Toolkit da propia instancia.

    3. Unha vez que se reinicie a instancia, nun terminal comproba que docker apareza na listaxe de grupos. 

      $ groups
ubuntu adm ... lxd docker

    4. Exporta o token que subiches no apartado anterior a unha variábel de ambiente.

      Nota

      Usa o nome do ficheiro do teu token no comando.

      $ export AWSIOT_TUNNEL_ACCESS_TOKEN=$(cat ~/secure_tunnel/<O_TEU_TOKEN_ID>-sourceAccessToken.txt)

    5. Comproba no mesmo terminal que a variábel está correctamente configurada.

      $ echo $AWSIOT_TUNNEL_ACCESS_TOKEN

      Token exportado nunha variábel de ambiente.

      Importante

      A variábel de ambiente non é permanente. Se pechas o terminal terás que volver exportala.

    6. No mesmo terminal no que exportaches o token crea a conexión ao túnel seguro executando a imaxe Docker do proxy local.

      Nota

      A explicación dos parámetros que se lle pasan ao localproxy podes vela aquí.

      $ docker run --rm -it --network=host \
    -e AWSIOT_TUNNEL_ACCESS_TOKEN=$AWSIOT_TUNNEL_ACCESS_TOKEN \
    public.ecr.aws/aws-iot-securetunneling-localproxy/ubuntu-bin:amd64-latest \
    --region us-east-1 -s 5555 -c /etc/ssl/certs --destination-client-type V1

      Execución do proxy local nun contedor Docker.

    7. Verifica na consola do AWS IoT que nas propiedades do túnel agora aparecen ambas conexións (orixe e destino) en verde.

      Propiedades do túnel seguro na consola do AWS IoT.

    Importante

    Antes de continuar toma as capturas 3 e 4 que se piden para xustificar a actividade.

    Conexión ao dispositivo IoT

    Unha vez que temos o proxy local no dispositivo orixe conectado ao túnel seguro, vamos usar esa conexión para abrir unha sesión SSH co dispositivo IoT destino. Fai o seguinte:

    1. Abre outro terminal na instancia orixe e configura un par de chaves SSH usando EC2.

      Nota

      Usa o teu prefixo no nome do ficheiro que almacena as chaves.

      $ cd ~/secure_tunnel
$ aws ec2 create-key-pair --key-name secure-tunnel > <O_TEU_PREFIXO>-key-pair.json
$ EC2_KEY_MATERIAL=$(jq -r ".KeyMaterial" <O_TEU_PREFIXO>-key-pair.json)
$ echo "$EC2_KEY_MATERIAL" > secure-tunnel.pem
$ chmod 400 secure-tunnel.pem

      Configuración das chaves SSH na orixe.

    2. Na instancia do dispositivo IoT destino (onde está instalado o Device Client), adiciona a chave creada no punto anterior no ficheiro de chaves SSH permitidas.

      $ aws ec2 describe-key-pairs --key-names secure-tunnel --include-public-key \
    --output text --query "KeyPairs[0].PublicKey" >> ~/.ssh/authorized_keys

      Configuración das chaves SSH permitidas no dispositivo IoT.

      Nota

      Nun escenario real o dispositivo IoT xa tería que ter previamente configuradas as chaves SSH permitidas, xa que non poderiamos acceder a el ao non ter aínda iniciada a conexión SSH a través do túnel seguro.

    3. Desde o terminal do paso 1 na instancia orixe, conéctate ao proxy local para iniciar a sesión SSH co dispositivo IoT destino a través do túnel seguro.

      $ ssh -i secure-tunnel.pem ubuntu@localhost -p 5555

      Sesión SSH remota ao dispositivo IoT a través do túnel seguro.

      Nota

      Fíxate en que ao establecer a conexión, a IP privada do prompt pasa a ser a da instancia 1 (o dispositivo IoT).

    Comprobación da conexión

    Se a conexión se realizou sen erros, agora estaremos conectados ao dispositivo IoT destino a través do túnel seguro. No terminal no que tes aberta a conexión SSH fai o seguinte:

    • Comproba o contido do ficheiro de configuración do Device Client. 
      $ sudo head -7 /etc/.aws-iot-device-client/aws-iot-device-client.conf
    • Comproba o estado do servizo Device Client. 
      $ sudo systemctl status aws-iot-device-client

    Importante

    Antes de continuar toma as capturas 5 e 6 que se piden para xustificar a actividade.

    Desconexión do dispositivo orixe

    1. No terminal da instancia orixe no que tes aberta a conexión SSH co dispositivo IoT destino, pecha a conexión co comando: exit.

    2. No mesmo terminal, detén a execución do contedor Docker do proxy local. 

      $ docker stop $(docker ps -q)

      Nota

      Se o contedor Docker do proxy local se detivo correctamente, no terminal onde estaba a executarse agora terás un prompt do shell agardando por un comando. Se executas docker ps -q non debería devolver nada na saída.
